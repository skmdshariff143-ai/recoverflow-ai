## 1. Executive Summary

This forensic audit evaluates the initial codebase against the strict Track 3 requirements:
> *"Detect revenue at risk, determine the right intervention, execute a bounded recovery workflow, and show measured money recovered across a batch with compliant escalation, stopping rules, and an audit trail."*

While the existing codebase demonstrates solid modularity (clean TypeScript interfaces, Next.js 16 App Router, Tailwind CSS, 78 passing unit tests, and Playwright E2E tests), the forensic inspection confirms **critical methodological defects, circular evaluation logic, naming discrepancies, and missing integration boundaries** that must be rigorously addressed to achieve an honest, defensible, production-grade submission.

## 2. Forensic Findings & Risk Analysis

### Finding 1: Circular Calibration Defect in Outcome Simulation (CRITICAL)
- **Source Code**: `src/lib/engine/executeIntervention.ts` (lines 86–92)
  ```typescript
  const outcomeProb = item.score.recovery_probability;
  const isSuccess = rng() < outcomeProb;
  ```
- **Analysis**: The simulation generator produces synthetic recovery outcomes by sampling directly from the model's **own predicted recovery probability** (`item.score.recovery_probability`).
- **Impact**: Measuring calibration (predicted rate vs actual rate) against outcomes generated by the prediction itself is mathematically circular. It proves that the seeded PRNG accurately samples Bernoulli distributions, but **does not prove independent predictive validity**.
- **Required Correction**: Decouple the Decision Model from a separate, frozen **Outcome Environment** driven by independent latent factors and empirical transition matrices that never read model predictions or Expected Values.

---

### Finding 2: Product Identity & Repository Naming Split
- **Source Code**: `package.json`, `src/app/page.tsx`, `src/components/Header.tsx`, `README.md`
- **Analysis**: The GitHub repository is named `recoverflow-ai`, but `package.json` was titled `payback-ai` and the UI referred to `PayBack AI`.
- **Impact**: Creates confusion for evaluators and breaks naming consistency across artifacts and deployment targets.
- **Required Correction**: Standardize the entire project as **RecoverFlow AI** across all package metadata, components, headings, tests, documentation, and accessible ARIA attributes.

---

### Finding 3: Single-Shot Simulation vs Closed-Loop Multi-Cycle State Machine
- **Source Code**: `src/lib/engine/executeIntervention.ts`
- **Analysis**: Current execution evaluates a single simulated attempt per payment. If the attempt fails, it marks `retry_scheduled` or `stopped`, but does not simulate a continuous closed-loop state machine (`DETECTED -> DIAGNOSED -> ELIGIBILITY_CHECKED -> APPROVAL_REQUIRED / SCHEDULED -> EXECUTING -> OUTCOME_OBSERVED -> RETRY / RECOVERED / PROMISE_TO_PAY / STOPPED`).
- **Required Correction**: Implement a genuine multi-cycle state machine with idempotent transitions, backoff scheduling, alternative interventions (e.g. switching from retry to payment link reminder), and a Promise-to-Pay lifecycle tracker.

---

### Finding 4: Lack of Razorpay Test-Mode Adapter & Mock Boundary
- **Source Code**: Entire repository
- **Analysis**: All execution currently happens in pure synthetic memory. There is no official Razorpay test-mode API adapter boundary (`RecoveryExecutionAdapter`).
- **Required Correction**: Implement an adapter pattern with:
  1. `DeterministicSimulatorAdapter` (for local reproducible evaluation)
  2. `RazorpayTestModeAdapter` (server-side Razorpay test-mode customer contact/payment link creation via environment variables).

---

### Finding 5: Missing Bounded Gemini AI Diagnostic Layer
- **Source Code**: Entire repository
- **Analysis**: The app claims AI-powered diagnosis, but uses deterministic rule tables and logistic regression without invoking Google GenAI for unstructured error normalization or compliant message drafting.
- **Required Correction**: Integrate the official `@google/genai` SDK in a server-side route for unstructured gateway error categorization, communication drafting, and case summaries, guarded by strict circuit breakers and deterministic fallbacks.

---

### Finding 6: Memory-Only Audit Log vs Append-Only Hash-Chained Ledger
- **Source Code**: `src/lib/engine/auditTrail.ts`
- **Analysis**: Audit records are dynamically computed in React memory (`useMemo`) during render rather than being an immutable, append-only, SHA-256 hash-chained ledger.
- **Required Correction**: Implement a cryptographic SHA-256 event hash chain with tamper detection (`verifyLedgerIntegrity`) and exportable signed-style batch reports.

---

### Finding 7: Monetary Integer-Paise Precision & Currency Segregation
- **Source Code**: `src/lib/engine/scoreRecovery.ts`, `src/lib/engine/runBatch.ts`
- **Analysis**: While amounts in the synthetic generator are in paise (`100_000`), various components perform floating-point divisions (`/ 100`) and format with `.toFixed(2)` before arithmetic summation.
- **Required Correction**: Enforce strict integer-paise representation throughout all engine calculations:
  $$\text{expectedValuePaise} = \text{round}\left(\frac{\text{amountAtRiskPaise} \times \text{probabilityBps}}{10,000}\right)$$
  Enforce strict INR-only dataset constraints or currency segregation.

---

### Finding 8: Absence of a Baseline Control Policy Comparison
- **Source Code**: `src/lib/engine/calibration.ts`
- **Analysis**: RecoverFlow AI is only benchmarked against itself (heuristic vs logistic), but not against a standard industry **Control Policy** (e.g. Fixed Retry Schedule / Retry-All without EV prioritization).
- **Required Correction**: Implement counterfactual policy evaluation comparing RecoverFlow AI against a Fixed Retry Control on the exact same frozen potential outcomes.
